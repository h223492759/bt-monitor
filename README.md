# 蓝牙监控 · bt-monitor

荣耀手机蓝牙自动关闭，写个工具监控来分析

一个只做一件事的 Android 小工具：**长时间、无人值守地记录蓝牙（以及飞行模式 / Wi-Fi / 移动网络 / 屏幕 / 充电）的状态变化**，落成纯文本，便于事后用脚本分析。

它最初是为了回答一个具体问题：

> 荣耀 Magic7 Pro 的蓝牙会“自己关掉”。到底是**崩溃**还是**被关**？是**系统**问题还是**芯片**问题？

adb 只能盯几十分钟，手机一拿走就断。所以做成 App，能跟着手机跑一周。

## 一、它记录什么

| 类别 | 内容 |
|---|---|
| 蓝牙 | 适配器状态变化（OFF / TURNING_ON / ON / TURNING_OFF）、**本次 ON 已持续秒数**、**开启尝试次数 / 成功次数**、**非人为关闭次数（区分"运行中掉线"与"启用阶段就失败"）**、**"想开却没开"持续时长**、本机蓝牙名 |
| 飞行模式 | 开 / 关 |
| Wi-Fi | Wi-Fi 开关状态、期望状态、SSID、RSSI |
| 移动网络 | 当前承载（WIFI / CELLULAR / NONE）、蜂窝是否可用、移动数据期望开关 |
| 其他 | 屏幕亮灭、充电插拔、开机、服务启停、网络可用性变化 |

采样分两类：

- **HB（周期采样）**——默认每 60 秒一行，把所有字段的快照写下来；
- **EV（状态变化）**——状态一变就写一行，不丢事件。

## 二、日志格式（关键，方便外部脚本解析）

文件按天切分，位于 App 外部私有目录：

```
/sdcard/Android/data/com.lhj.btmonitor/files/btlog/btmon-YYYY-MM-DD.txt
```

也可以在 App 里一键**导出 TXT 到「下载」目录**：

```
内部存储/Download/bt-monitor/btmon-export-YYYYMMDD-HHmm.txt
```

每行形如：

```
15:20:11.123 HB|src=tick|bt=ON|btSet=1|btUp=1699|btName=My Phone|ap=0|wifi=ENABLED|wifiSet=1|ssid=MyWiFi|rssi=-45|cell=1|net=WIFI|mdata=1|scr=OFF|batt=85|chg=Y|up=12345|crash=3
15:21:02.440 EV|bt_try|第4次尝试开启|prev=OFF
15:21:02.456 EV|bt_adapter|OFF->TURNING_ON|btSet=1
15:21:02.460 EV|bt_adapter|TURNING_ON->ON|btSet=1
15:21:02.461 EV|bt_ready|reached_ON|btName=My Phone|尝试=4 成功=1 崩溃=3(启用阶段=3)
15:29:31.900 EV|SUSPECT_CRASH|mode=ON_ENABLE TURNING_ON->OFF 系统期望仍为开(btSet=1) 非人为关闭|尝试=5 成功=1 崩溃=4(启用阶段=4)
15:29:31.905 EV|STUCK_OFF|当前处于「系统期望开、实际却没开」的异常态 bt=OFF btSet=1|尝试=5 成功=1 崩溃=4(启用阶段=4)
15:40:02.100 EV|STUCK_OFF_END|已脱离「想开没开」状态 持续=630s
```

### 字段表

| 字段 | 含义 |
|---|---|
| `bt` | 蓝牙适配器态：`OFF` / `TURNING_ON` / `ON` / `TURNING_OFF` |
| `btSet` | 系统的“期望值”（读 `Settings.Global.bluetooth_on`）：1 = 想开，0 = 想关，**2 = 被飞行模式压制**（实测 2026-09-20 22:09：开飞行模式那一刻适配器被关，但设置值是 2 而不是 0） |
| `btUp` | **本次进入 ON 后已持续秒数**；-1 表示当前不在 ON |
| `btName` | 本机蓝牙名（需要蓝牙权限，否则为 `-`） |
| `ap` | 飞行模式 1/0 |
| `wifi` / `wifiSet` | Wi-Fi 实际态 / 期望态 |
| `ssid` / `rssi` | 当前 Wi-Fi 名 / 信号（无定位权限时通常为 `?`） |
| `cell` / `net` | 蜂窝是否可用 1/0 · 当前承载 |
| `mdata` | 移动数据期望开关 1/0 |
| `scr` | 屏幕 ON / OFF |
| `batt` / `chg` | 电量百分比 / 是否在充电 |
| `up` | **监控服务自身已运行秒数** —— 若出现大跳跃，说明监控曾被杀/被冻结，那段数据不可信 |
| `crash` | 非人为关闭累计次数 |

### 关键事件（分析时主要看这几类）

| 事件 | 含义 |
|---|---|
| `EV\|bt_try` | 一次开启尝试（进入 `TURNING_ON`）。统计 `尝试=N` |
| `EV\|bt_ready` | **成功到达 ON**，并带上累计统计 `尝试=N 成功=M 崩溃=X(启用阶段=Y)` |
| `EV\|SUSPECT_CRASH` | **非人为关闭**。`mode=WHILE_ON`（开成功后运行中掉线）/ `mode=ON_ENABLE`（启用阶段就失败）。⚠️ 一次适配器重启**只记 1 条** |
| `EV\|SUSPECT_CRASH_MORE` | 同类崩溃仍在持续，`burst=` 为 60 秒内的重复次数（防刷屏） |
| `EV\|STUCK_OFF` | 采样时发现「系统期望开、实际却没开」——**这正是“根本打不开”的形态**。需持续 ≥2 个采样周期才落盘（避开“刚点开、适配器还在转”的正常窗口） |
| `EV\|STUCK_OFF_END` | 脱离上述状态，`持续=Ns` 即卡了多久 |
| `EV\|bt_off_by_user` | 人为关闭（`btSet` 变 0），与崩溃区分用 |
| `EV\|shutdown` | **收到系统关机/重启广播**（`ACTION_SHUTDOWN` / `ACTION_REBOOT`，服务内**动态注册**），带 `已当场撤销=N`。关机误报的**第一现场** —— 拿到它就能当场撤销那笔误报，不必等下次开机反推 |
| `EV\|REBOOT_DETECTED` | 设备曾关机/重启。**双通道判定**：① 关机/重启广播（实时）；② 单调钟 `elapsedRealtime` 被复位（只有重启会复位它，**不依赖任何广播**，服务被系统杀掉也能自证）。并自动撤销关机造成的误报崩溃 |
| `EV\|COUNT_ADJUSTED` | **计数被回正**，格式 `旧值->新值`。任何撤销都落这一行，**可回查、可审计、不静默**。关机时它可能出现在两处：紧跟 `EV\|shutdown`（广播先到）或紧跟 `EV\|SUSPECT_CRASH`（掉线先到）—— **两条通道互相独立、先后随机，两种顺序都正常** |
| `EV\|CLOCK_JUMP` | 墙钟被调整（NTP 校时 / 手动改时间）。**不是**重启，不撤销任何计数 |
| `EV\|airplane` | 飞行模式开关（实时。服务内**动态注册**） |
| `EV\|screen` | 屏幕亮灭 / 解锁（实时。服务内**动态注册**） |
| `EV\|power` | 充电插拔（实时。服务内**动态注册**） |
| `EV\|wifi` | Wi-Fi 开关（实时。服务内**动态注册**） |
| `EV\|net` | 网络承载变化，格式 `caps=旧->新\|held=旧值持续秒数`。同值重复回调**已去重** |

> 上面标了「动态注册」的几类，**manifest 静态注册是收不到的**（实测两天 0 条）。
> 详见下面「为什么有些事件过去记不到」。

### 「非人为关闭」是怎么判定的

```
蓝牙从 ON / TURNING_ON 掉到 OFF/TURNING_OFF   且   btSet(系统期望) 仍然 = 1
```

两条同时成立 ⇒ 不是人关的（人关会把 `btSet` 置 0），而是**协议栈自己崩了**。

> ⚠️ 这里有两点很容易踩：
>
> **① 不要求“上一态必须是 ON”。** 本机最主要的故障形态是**根本开不起来**
> （`OFF → TURNING_ON → OFF`，初始化阶段就崩，从不经过 ON）。只认 `ON→OFF` 的话，
> 这类崩溃会 100% 漏记 —— 而那恰恰是最该被记录的情况。
> 所以判定分成 `mode=WHILE_ON`（运行中掉线）与 `mode=ON_ENABLE`（启用阶段失败）两种。
>
> **② 一次崩溃只记 1 条，不是 2 条。** 一次适配器重启的完整序列是
> `ON → TURNING_OFF → OFF → TURNING_ON → ON` —— 只有「离开 ON/TURNING_ON 的那一跃」才是本次崩溃，
> 紧随其后的 `TURNING_OFF→OFF` 属于同一次。旧版把这两跃各记一次，导致**`crash` 计数虚高一倍**
> （实测导出日志里 30 条 `SUSPECT_CRASH` 实际只对应 15 次事件）。
> 只影响 `crash`：`尝试` / `成功` / `启用阶段失败` 旧版本就没有重复累加，数值本来就是准的。

另一种没有任何状态跃迁可捕获的情况是：**进 App 之前蓝牙就已经卡在“想开没开”**。
这由周期采样兜底，记为 `STUCK_OFF`。

### 关机为什么会**多记**一笔崩溃（v1.0.6 / v1.0.7 修）

关机 / 重启时系统会先关掉蓝牙适配器，而那一刻 `Settings.Global.bluetooth_on` **仍是 1**
（实测 2026-09-20 22:09 开飞行模式的一瞬甚至读到 `btSet=2`），
于是这次掉线被记成一笔「非人为关闭」，**凭空多 1 笔崩溃**。

判据要**同时**满足（关键在 ①）：

1. **该笔之后再没恢复过** —— 真崩溃时系统会自己把适配器重启回来
   （实测形态 `ON→TURNING_OFF→OFF→TURNING_ON→ON`，1~3 秒）；关机则永远回不来。
2. 它紧贴上一次采样，窗口要**两侧都放宽**（2 个采样周期）。
   ❗实测那次 `crash 22:10:02.309` 落在**最后一拍 22:10:03.753 之前 1.4 秒** ——
   旧版只判「在上一拍之后」（单侧），于是漏撤、计数永久多 1。
3. 与当前时刻相距 < 10 分钟（防墙钟被 NTP 调整造成的时间乱序）。

撤销一律落 `EV|COUNT_ADJUSTED`。

#### 补一刀：为什么「拿到广播就能当场撤销」还不够（v1.0.7 修）

**系统关蓝牙** 和 **发 shutdown 广播** 是两条**互相独立**的通道，谁先谁后**随机** ——
实测 2026-09-20 22:41:31.**183** 广播先到、31.**187** 掉线后到，只差 **4ms**。

v1.0.6 只写了「广播到达时撤销**已有的**那笔」，是**单向**的：广播先到时必然扑空
（那一刻还没有崩溃可撤），于是那笔误报要一直等到**下次开机**靠自证反推 ——
实测确实如此：关机那刻计数多 1（`崩溃=18`），3 分 20 秒后开机才回正成 17。

v1.0.7 改成**双向缝合**：广播一到就落一个 10 秒时间窗标记（`shutdown_marker`），
**崩溃一记下就回查它**并当场撤销。两种先后都能覆盖：

```
广播先到 → 撤销扑空 → 落标记 → 掉线记崩溃 → 回查命中 → 当场撤销
掉线先到 → 记崩溃 → 广播到 → 撤销已有的那笔（标记同时清掉）
```

> 同一类错误在本项目出现过两次：上次是「撤销窗口只判单侧」（只看崩溃在采样**之后**）。
> 教训一致 —— **两个独立通道之间的时序假设，必须双向缝合，不能只写一个方向。**

另外对**历史残留**做一次性回正
（`repairShutdownArtifactFromLog`）：回日志里找 `REBOOT_DETECTED` + 紧邻的 `SUSPECT_CRASH`
+ 其后无任何恢复 + 该笔计数等于当前值 —— 四条同时成立才减 1，
**找不到证据就什么都不做**（不回正、不猜测）。

> 刻意留的取舍：若「真崩溃后适配器一直没起来」且用户又在 2 个采样周期内重启了设备，
> 这笔真崩溃会被一起撤掉（少记 1）。两害相权 —— 宁可偶尔少记这种极端情况，
> 也不要**每次关机都平白多记一笔**。

### 关于「崩溃」这个词 —— 它到底是什么

指的是**手机系统的蓝牙服务把这个适配器重启了一遍**（系统侧日志里就叫 `Bluetooth crashed`）：
**不是本 App 崩溃，也不是蓝牙被关掉不回来**。

完整形态 `ON → TURNING_OFF → OFF → TURNING_ON → ON`，实测通常 **1~2 秒**就自动恢复
（15 次里 12 次如此），状态栏图标闪一下即回，用户基本察觉不到。
少数会卡得久一些：实测最长一次掉线后**卡了 49 分钟**才回来。

至于**为什么崩**，**目前没有可靠结论**。

> ⚠️ 这里原先写过「15 次里 13 次（87%）崩溃前 90 秒内有 Wi-Fi 承载剧变」，**该结论已撤回**。
> 它是拿**未去噪**的网络回调算的：旧版 `EV|net` 每秒把同一个值重复写一遍（两天 3982 行 ≈ **26 秒一条**），
> 于是 90 秒窗口的**期望命中就有 3.4 条** —— 命中率必然趋近 100%，
> 算出来的是「事件密度」，不是「相关性」。
>
> 把噪声去重到「承载值真的变化」后只剩 28 次；崩溃按物理事件去重得 17 次、再去簇（<10 分钟算一簇）得 **9 簇**，
> 命中仅 **1/9（11%）**，而且那 1 簇本身就是「19 分钟内连崩 9 次」的异常态。
> v1.0.5 段的 2 次独立崩溃，前 90 秒**没有任何承载变化**。
> ⇒ 「Wi-Fi 剧变 → 蓝牙崩溃」只能算**未证实的猜想**，要坐实仍需厂商 HAL / 固件层日志。
>
> 教训：**别拿带噪声的事件流做时间邻接统计** —— 当事件平均间隔小于判定窗口时，命中率必然趋近 100%。

### 为什么有些事件过去记不到（v1.0.5 修）

`AndroidManifest.xml` 里曾静态注册 11 个 action，跑两天后按 action 数条数，
**只有蓝牙状态变化（86 条）和开机广播（2 条）真正到达**，其余全部 0 条 ——
飞行模式、关机、屏幕、电源、Wi-Fi 开关一个都没记到，接收器里那些分支等于死代码
（`ACTION_SCREEN_ON/OFF` 从 Android 8 起更是只允许动态注册）。

v1.0.5 起这些通道**全部改到常驻服务里 `registerReceiver` 动态注册**，manifest 只留真正有效的两条。
v1.0.6 又给关机加了**双保险**：关机/重启广播（第一现场，实时撤销误报）
＋ `elapsedRealtime` 复位自证（不依赖广播，服务即使被系统杀掉也能反推）—— 两条互相兜底。

### 与系统侧计数交叉验证（推荐）

App 只能看到 Android 框架暴露的状态。系统自己还有一份**权威计数**，在电脑上跑：

```bash
adb shell dumpsys bluetooth_manager | grep -A30 "Enable log"
adb shell dumpsys bluetooth_manager | grep "crashed"
```

其中 `Disable ... CRASH BluetoothSystemServer` 行就是每次崩溃的原始记录，
`Bluetooth crashed N times` 是系统累计总数。拿它和 App 的 `crash=` 对照，
两者应当量级吻合。

## 三、构建

### 方式 A：GitHub Actions（推荐，零本地环境）

推 tag 即出 APK，并自动创建 Release（tag 约定 `vYYMMDD-HHMM`，如 `v260919-1740`）：

```bash
git tag v260919-1740
git push origin v260919-1740
```

也可以在 Actions 页面手动 `Run workflow`。

### 方式 B：本地构建

需要三样东西（都可用免安装 zip 版）：

| 工具 | 用途 | 官方下载 |
|---|---|---|
| JDK 17 | 编译 Kotlin / Gradle 运行 | https://adoptium.net/temurin/releases/?version=17&os=windows&arch=x64 |
| Android SDK Command-line Tools | 提供 `sdkmanager` 与平台包 | https://developer.android.com/studio#command-line-tools-only |
| Gradle 8.13 | 构建系统；也可用它 `gradle wrapper` 生成 wrapper | https://gradle.org/releases/ |

装完 SDK 后还需装平台包：

```bash
sdkmanager --install "platform-tools" "platforms;android-35" "build-tools;35.0.0"
```

然后在项目根目录写 `local.properties`：

```properties
sdk.dir=D\:\\AndroidDev\\sdk
```

构建：

```bash
gradle assembleRelease
```

> 本仓库**没有提交 gradle wrapper**（`gradlew` / `gradle-wrapper.jar`）——CI 用
> `gradle/actions/setup-gradle` 指定版本构建，本地用你自己装的 Gradle。
> 想要 wrapper 就在项目根目录跑一次 `gradle wrapper --gradle-version 8.13`。
> 注意：用 `gradle` 命令时项目根目录必须有 `local.properties`（见上）。

产物：`app/build/outputs/apk/release/app-release.apk`

> **签名**：release 用一把**固定**的密钥库（CI 上从 GitHub Actions Secret
> `DEBUG_KEYSTORE_B64` 还原，构建时由 `app/build.gradle.kts` 里的显式
> `signingConfig` 指定）。各版本证书完全一致，可直接覆盖安装升级。
> 注意**光把密钥库文件放到 `~/.android/debug.keystore` 是不够的** —— AGP 默认解析
> 在 CI 上签出的证书会不同，必须显式指定签名配置。如需正式签名，换掉那一段即可。

## 四、装到手机后必须做的 4 步（否则跑不满一周）

MagicOS / EMUI 默认会清理后台：

1. **应用启动管理** → 找到「蓝牙监控」→ 关掉「自动管理」→ 允许自启动 / 关联启动 / 后台活动
2. **电池** → 应用省电策略 → 设为「不受限制」（或允许后台高耗电）
3. **最近任务** 里下拉卡片锁定（加锁），避免被一键清理
4. App 内点一次「申请忽略电池优化」并同意

装好后 App 会自动开始监控（默认 60 秒一采）。

### 怎么看它到底有没有在干活

界面第一屏顶部有两行，**这是判断监控是否存活的唯一可靠依据**：

```
服务      : 运行中   本次运行 1h12m
最后采样  : 37 秒前
```

- `最后采样` 正常应是**几十秒**（略大于采样间隔）。若显示成分钟级，并带
  `⚠ 采样已停滞！请点「停止」再「开始」`，说明服务虽然活着但已经不产数据了。
- 千万不要只看通知栏那句"监控运行中"——**通知在 ≠ 在采数据**（见下）。
- 事后分析看日志里的 `up` 字段是否连续。

### 服务自愈（v1.0.4 起）

早期版本有一个坑：如果监控是在**「进程被杀之后、由某个入口把服务拉起来」**的情况下启动的
（典型场景就是**覆盖安装新版本**），服务会变成**「空壳」**——通知栏照旧显示"监控运行中"、
进程也活着，但一条数据都不写，日志凭空断掉，且没有任何报错。

v1.0.4 修掉了这个（所有启动分支都会完整初始化），并加了三道保险：

1. **看门狗闹钟**：每 3 个采样周期排一次 `setAndAllowWhileIdle`，发现采样停了就自动补一拍并恢复；
   健康时只重排闹钟、**不写任何日志**，不会污染 60 秒节奏。
2. **打开 App 即自愈**：只要把 App 切到前台，发现服务没在跑就自动拉起来。
3. **状态广播自愈**：蓝牙/屏幕/电源等状态变化时顺带检查一次（判据是"最近有没有出数据"，
   而不是一个会过期的"运行中"标记）。

> ⚠️ 荣耀实测**不会**投递 `MY_PACKAGE_REPLACED`，所以**升级安装之后服务不会自动回来，
> 需要手动打开一次 App**（App 会自动恢复）。升级完请顺手看一眼「最后采样」。

## 六、局限（写清楚，免得误导）

- **系统能杀服务**：厂商省电策略可能在长时间灭屏后冻结或杀掉本 App。日志里的 `up` 字段就是用来发现这件事的。
  设备进入 Doze（灭屏 + 未充电）时，`Handler` 定时器会被挂起 ⇒ 采样会出现**整段空洞**。
  v1.0.4 起有看门狗闹钟兜底，但 Doze 下闹钟也只能等到维护窗口才触发，所以**别指望灭屏时仍然 60 秒一行**。
- **`STUCK_OFF` 的误报**（v1.0.5 已缓解）：系统写 `bluetooth_on=1` 与适配器真正开始 `TURNING_ON`
  之间有天然延迟（实测点开关后约 47 秒），采样恰好落进这个窗口就会多写一行。现要求
  **持续 ≥2 个采样周期**才落盘，且时长仍从第一次发现的时刻起算（不牺牲真实性）。
  它只影响这个辅助事件，**不影响 `SUSPECT_CRASH` 主判据**。
- **`ssid` 需要定位权限**，不给也能跑，只是 Wi-Fi 名记不到。
- **`mdata`（移动数据期望值）** 在部分 ROM 上读不到，会是 -1，不影响 `cell`（蜂窝是否可用）的判断。
- **采样粒度分日夜两段**：屏幕活跃时 60 秒一格；夜间灭屏进 Doze 后退化到**约 300 秒一格**。
  系统限制，改不掉 —— 所以**事件类信息一律走广播实时落盘**，不要靠采样行去推断。
  判断服务是否断档看 `HB` 的 `up` 连续性；判断事件是否发生只看 `EV` 行。
- **`crash` 是"框架可见的"非人为关闭次数**，不等于系统内部计数。系统还会记录一些 App 层看不到的
  协议栈重启（例如荣耀关闭蓝牙后底层停在 `BLE_ON`）。做严谨结论时请按第二节那条 adb 命令
  取系统侧 `Bluetooth crashed N times` 交叉验证。
  ⚠️ 系统那个数是**累计值**（可能从上次刷机/清空起算），不要直接和 App 的当日计数比大小。
- **v1.0.5 对历史 `crash` 计数做过一次回正**（旧版一次崩溃记两条 ⇒ 数值虚高一倍，现按 2 整除）。
  `尝试` / `成功` / `启用阶段失败` 三个计数**不受影响** —— 旧版对它们没有重复累加，本来就是准的。
- **无法区分“固件崩溃”与“驱动/固件层其他异常”** —— App 只能看到 Android 框架暴露的状态。要再往下结论，仍需 adb / tombstone。
